# Deployment

How LearnSphere runs in production: **MongoDB Atlas** (database), **Render** (API with the video worker inside, plus a Redis-compatible Key Value store), **Vercel** (React client). Razorpay is in test mode. Paths below assume this project lives in the `FS-03` folder of the repository.

## 1. MongoDB Atlas

1. In an existing project and cluster, open **Database Access**, add a user `learnsphere_user` with a new password (letters and numbers only, so the connection string needs no escaping).
2. Give it **Specific Privileges**: role `readWrite` on database `learnsphere` only. The user cannot touch other databases in the same cluster.
3. **Network Access**: `0.0.0.0/0` is needed because Render's outgoing IPs change on the free plan.
4. **Connect > Drivers**: copy the string and put the database name before the `?`:
   `mongodb+srv://learnsphere_user:<password>@<cluster>.mongodb.net/learnsphere?retryWrites=true&w=majority`

## 2. Redis for the video queue

BullMQ needs Redis. On Render create a **Key Value** instance in the same region as the API and use its **internal** URL as `REDIS_URL`. In its settings set the max memory policy to **noeviction**; BullMQ warns when keys can be evicted, and evicted job keys would lose videos in the queue.

## 3. API on Render

Create a **Web Service** from the repository:

| Setting | Value |
| --- | --- |
| Root directory | `FS-03/server` |
| Runtime | Docker (uses `server/Dockerfile`, which installs FFmpeg and a font) |
| Region | same as the Key Value instance |
| Health check path | `/api/health` |

A free instance cannot run a separate background worker, so the worker runs inside the API process (`RUN_WORKER_INLINE=true`). `render.yaml` at the repository root describes the same setup if you prefer a Blueprint.

Environment variables:

| Variable | Value |
| --- | --- |
| `NODE_ENV` | `production` (strict env checks, secure cookies with `SameSite=None`) |
| `MONGO_URI` | Atlas string from step 1 |
| `REDIS_URL` | internal URL from step 2 |
| `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`, `MEDIA_SIGNING_SECRET` | three long random strings (`openssl rand -hex 32`) |
| `CLIENT_URL` | the Vercel URL, no trailing slash (comma-separate several) |
| `PUBLIC_API_URL` | the API's own public URL, used in signed video links |
| `RUN_WORKER_INLINE` | `true` |
| `SEED_DEMO` | `true` (seeds an empty database once and rebuilds the demo video when the disk was wiped) |
| `STORAGE_DRIVER` | `local` (see the storage section) |
| `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, `RAZORPAY_WEBHOOK_SECRET` | test-mode keys from step 5 |

Check it: `curl https://<api>/api/health` should return `"status":"ok","db":"connected"`.

## 4. Client on Vercel

Import the repository, set **Root Directory** to `FS-03/client`. Build command `npm run build`, output `dist`. Add the environment variable `VITE_API_URL=https://<api>` (no trailing slash) and redeploy, because Vite reads it at build time. `vercel.json` rewrites every path to `index.html` so deep links work. After the first deploy copy the Vercel URL into `CLIENT_URL` on Render.

## 5. Razorpay (test mode)

1. Razorpay Dashboard: switch to **Test Mode**, then Account & Settings > API Keys > generate a key pair. The same test keys can be used by several projects.
2. Put `RAZORPAY_KEY_ID` (starts with `rzp_test_`) and `RAZORPAY_KEY_SECRET` on Render. The secret is shown only once.
3. Webhooks > add `https://<api>/api/payments/webhook`, events `payment.captured`, `order.paid`, `payment.failed`, and a secret of your choice, which goes into `RAZORPAY_WEBHOOK_SECRET`.
4. Pay for a course with a test card from Razorpay's documentation (for example the Mastercard test number listed there, any future expiry, any CVV). Test UPI works with `success@razorpay`.

## Storage on the live site

The code supports two drivers. `local` writes videos to the server's disk. `s3` writes to a bucket and can deliver through CloudFront signed URLs.

This deployment uses `local`, because I do not have an AWS account. On Render's free plan the disk is wiped on every restart and sleep, so:

- the seeded demo video is rebuilt at start-up when `SEED_DEMO=true` (the title card is generated by FFmpeg, about a minute on the free CPU)
- a video uploaded on the live site works until the next restart

If you have AWS, set `STORAGE_DRIVER=s3` and the variables below.

### S3 and CloudFront (optional)

1. Private S3 bucket with public access blocked.
2. CloudFront distribution with the bucket as origin (Origin Access Control). For `videos/*` set **Restrict viewer access** with a trusted key group.
3. Create a public key and key group, keep the private key for `CLOUDFRONT_PRIVATE_KEY` (newlines written as `\n`) and the key ID for `CLOUDFRONT_KEY_PAIR_ID`.
4. Add CORS for the client origin on the bucket and a CORS response policy on CloudFront.
5. Signed cookies only work when the CDN hostname shares a parent domain with the app, for example `cdn.example.com` and `app.example.com`. Set `VITE_CDN_COOKIE_DOMAIN=.example.com` on the client.

Server variables: `STORAGE_DRIVER=s3`, `S3_BUCKET`, `S3_REGION`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `CLOUDFRONT_DOMAIN`, `CLOUDFRONT_KEY_PAIR_ID`, `CLOUDFRONT_PRIVATE_KEY`.

## Docker locally

`docker compose up --build` starts Mongo, Redis, the API, a separate worker and an nginx container that serves the client on http://localhost:8080 and proxies `/api` and `/socket.io`. Put values in a `.env` file next to `docker-compose.yml` (see `.env.example`). To use Atlas instead of the local Mongo container, set `MONGO_URI` there.

## Things to remember

- The free Render service sleeps after about 15 minutes without traffic. Open the health URL a few minutes before a demo.
- Live classes need a camera and microphone permission and use STUN only. Set `TURN_URL`, `TURN_USERNAME` and `TURN_CREDENTIAL` to add a TURN server.
- Seeding runs only when the `users` collection is empty, so it never overwrites real data.
